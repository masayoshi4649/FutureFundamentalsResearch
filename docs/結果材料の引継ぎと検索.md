# 結果材料を次のブラインド予測へ渡す

- 第20場の結果ニュースレビューから利用する。元case・予測材料点・採点・snapshotは上書きしない。
- 実行補助：`local/本文遮断連続/結果材料を引き継ぐ.py` の `作成(memory, base_path, out, query_path=None)`。
- `base_path` は当回の既定直近12場の本文遮断版。既存追加検索を重ね掛けせず、追加検索時も同じ基底を指定する。
- `結果材料付きview.json` を当回actorの `feedback_snapshot_path` に渡す。主要欄は既存snapshotと同じ。各caseの `result_news_reactions` が結果レビューの別欄。
- 原reviewはcaseの `source_hashes` にある一意の `振り返り入力.json` をSHA・`review_hash`・予測/結果hashで辿る。
- manifest・可知性照合・本人読了のpath/SHA、原本・版・packet・時計・単一主文区間・本人実読を検査する。本文原本を本人へ再表示しない。
- 既存の満了・振り返り・運用記録時計、caseの根拠時計、snapshotの `review_visible` を守る。新根拠時計が後発なら、その最大時点まで結果材料を渡さない。
- 本人既読の当回 `audit.jsonl` だけは、開示までの３段階とreview後の４段階を別SHAで照合する。旧SHAは改行終端の先頭1230bytes等の実位置で確認し、全連鎖・現在末尾review・caseの現在SHAを検査。他ファイルにprefix例外を適用しない。
- 記事０なら、検索・全不採用理由を当回reviewと別根拠へ残し、`review_evidence`なしで旧reviewだけ渡す。読めた記事があっても `market_reaction_updates: []` を許容し、新索引・付加は０とする。
- 結果材料は「過去場の開示後に読んだ反応」。元の予測時点に知っていた材料へ遡及しない。
- 同じ場の２先物、続報・転載・同じ事象の再引用を独立な確証へ数えない。独立標本数は不明のまま。方向・点数・確率を自動生成しない。

## 古い結果材料を追加検索する

1. 本人が主導材料・比較目的・当回 `as_of`・`keywords`／`story_keys`／`channels` をJSONへ先に保存する。
2. 同じ基底を指定し、`query_path` にその事前JSONを渡して新しい保存先へ実行する。
3. 既存予測材料と、可知な結果材料の名前・主検索キー・関連検索キー・経路を照合する。一事例の最大一致値で順位を付け、同じ事象の重複ラベルを加算しない。
4. 一致値・満了時計・case_idの降順で最大30候補。基底重複を除いた先頭最大６場を追加する。成績・反応方向・反応量で選ばない。
5. `引継の来歴.json` にquerySHA・候補数・全候補順位・上限打切・元case/SHA・出力SHAを保存する。上限に達した場合は全履歴を網羅したと記さない。
6. 本人が元reviewと必要な結果材料を実読し、採否・相違点・今回への適用条件と反証条件を担当記録へ残す。自動選定を本人採用の申告へ代用しない。

- 検査：`test_結果材料の引継.py`。正常・未来・不整合・未読・空更新・新材料検索・当回監査の追記前後を確認する。
- 第20場の実物で５切出・３材料群の来歴照合を行い、第21場の別viewから導入する。
