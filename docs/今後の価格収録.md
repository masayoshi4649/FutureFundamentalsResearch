# 限月と受信時計を残す価格収録

- 状態：読取試行。新00016の予測・採点へ追加せず、既存CSVも変更しない。
- 2026/10/17 03:44の登録済み先物を照合し、NK225・TOPIXの銘柄コードと2026年12月限を確認した。過去CSVの全期間の限月を証明したものではない。
- 市場データ収集ツールの `kabus-controller.future_registrations` と `future_market_data` は今回の応答で読取専用。要求済み銘柄の登録・変更を行う取得口は使わない。
- 原応答、要求・収集時計、対象銘柄、限月を別フォルダへ保存した。価格値は予測担当へ表示していない。
- `CurrentPriceTime` は価格の時計、`collected_at` / `upstream_fetched` は収集の時計として分ける。銘柄別の鮮度を確認し、他先物を含む全体の最古時計を対象指数の鮮度へ転記しない。
- 今回の両対象の価格時計は03:44:22、収集は03:44:24。これは受信した一時点の記録であり、場全体の欠測を埋めるものではない。
- `PreviousCloseTime` は両対象とも日付の00:00だった。API仕様も日付項目として定義している。直前Day/Nightの終値時計や同先物P0へ自動代入しない。[APIの一次仕様](https://raw.githubusercontent.com/kabucom/kabusapi/master/reference/kabu_STATION_API.yaml)
- 同仕様の `ClearingPrice` は清算値。前セッションの引け約定値と同一視しない。`CurrentPriceStatus=8` は終値、23は板寄せ約定、別項目 `CurrentPriceChangeStatus=0061` は板寄り引け。これらの状態と実際の引け時計・日付・対象限月を照合する。[APIの一次仕様](https://raw.githubusercontent.com/kabucom/kabusapi/master/reference/kabu_STATION_API.yaml)
- 06時の引け前後にも登録１回・板６回を取得した。NK225の価格時計は06:00:01へ進んだが、TOPIXは06:01の追確認でも05:54:36だった。両対象の終値・板寄せ約定状態は確認できず、公式引けの収録成功とは扱わない。[取得結果](../local/前向き価格収録/引け試行_20261017/結果.md)
- 収集側の時計が要求完了時計より約３秒後だった。時計の未同期を残し、原値の補正や正確な受信時刻の断定をしない。
- 06:00:01を既存評価終端06:00へ丸めない。今回の板は別収録試行として保持し、固定済みのP0・結果へ差し込まない。今後の利用には限月・場・状態・時計の許容条件を持つ別版が必要になる。
- 将来の時点検証では、収集を予測締切より前に完了した版を使う。後から取得した過去時計の価格を、当時の受信記録として扱わない。
- この試行で通知・自動起動は設定していない。
